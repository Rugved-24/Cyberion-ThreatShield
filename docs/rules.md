# Detection rule contract and test harness

This is the reference for authoring and testing rules in this repository. It exists
so that a new analyst can write a rule and prove it works without reading
`scripts/test_all.py`.

## 1. One template, one harness

| Artefact | Purpose |
| --- | --- |
| `rules/_template.yml` | The only rule skeleton. Copy it; do not invent a second shape. |
| `scripts/test_all.py` | Syntax check, replay, negative assertion and correlation window matrix for **every** rule. |
| `scripts/tune.py` | Before-and-after false-positive measurement. Reuses the same matching code. |
| `scripts/build_coverage.py` | Derives the coverage matrix and Navigator layer from recorded results. |

There are no per-rule scripts. A new rule is one YAML file plus one row in
`detections/test-results.csv`, which is regenerated by the harness.

### Commands

```powershell
.\.venv\Scripts\python.exe scripts\test_all.py            # all rules
.\.venv\Scripts\python.exe scripts\test_all.py --rule CT-011   # one rule
.\.venv\Scripts\python.exe scripts\tune.py                # false-positive cases
.\.venv\Scripts\python.exe scripts\build_coverage.py      # coverage layer
```

`test_all.py` exits non-zero if any rule fails. `tune.py` exits non-zero if any
tuning case loses a declared attack match or leaves a residual benign match.

## 2. Required rule structure

Beyond the standard Sigma fields required by the product requirements document
(`title`, `id`, `status`, `description`, `references`, `tags`, `logsource`,
`detection`, `falsepositives`, `fields`, `level`), every rule carries four
`x-` extension blocks. `sigma check` ignores unknown top-level keys, and the
harness requires the first three.

| Block | Required | Purpose |
| --- | --- | --- |
| `x-attack` | yes | `framework` and the list of `techniques`. This is the coverage mapping. |
| `x-severity` | yes | `level` and a written `rationale`. A severity without a reason is not reviewable. |
| `x-scope` | yes | `covered` and `excluded`, both explicit. Prevents a rule silently claiming more than it does. |
| `x-evidence` | yes | `expected_event_uids`, `negative_event_uids` and a `note`. **This is what makes a rule testable.** |
| `x-benign-review` | yes | `cases`, `status` and a `note`. `status: pending` is honest and blocks a Covered claim. |
| `x-correlation` | correlation only | Parent, child, join field, window and the window-boundary matrix. |

### The evidence contract

`expected_event_uids` are full event UIDs of the form
`dataset_id:raw_sha256:record_locator`, for example
`DS002:968C4B699F7239D106577B2B8E206EDFAF812F193A60E663966258AF67A56ACC:1073`.

Rules about the evidence list:

- It is asserted, not merely reported. A rule whose declared evidence does not
  match is a **FAIL**, not a warning.
- `negative_event_uids` are records that must **not** match, usually siblings in the
  same telemetry scope. A rule whose declared negative matches is a **FAIL**.
- An **empty** `expected_event_uids` list is allowed and meaningful. It marks a rule
  written for a technique with no attacker instance in the available data, and it
  permanently prevents that technique from scoring above Not Covered. This is why
  CT-013 and CT-014 are at 0 and why the coverage builder refuses to promote them.
- Never write a UID you have not looked up. The raw SHA-256 is in
  `docs/DS001-inventory.json` and `docs/DS002-inventory.json`, and the line number
  is the physical line in the raw JSONL.

## 3. Supported condition grammar

Deliberately small, because a rule that cannot be replayed is a rule that has not
been tested.

```
condition: <name>
condition: <name> and <name>
condition: <name> or <name>
condition: not <name>
```

Anything else **raises and fails the rule** rather than silently matching nothing:
parentheses, `| count`, `| near`, `| all`, and field-reference conditions such as
`selection | field = image`. A failure here means the rule needs a different shape,
not a looser harness.

A selection is a mapping of field name to matchers. Fields are combined with AND;
multiple matchers for one field are combined with the quantifier (`all`, default
`any`).

| Modifier | Behaviour |
| --- | --- |
| `\|endswith`, `\|startswith`, `\|contains` | **Case-insensitive.** Sysmon records image paths with inconsistent casing, so case-insensitive is the correct default for path and command content. |
| `\|re` | **Case-sensitive** Python regular expression. Add `(?i)` for case-insensitive matching. Use this for switch and token boundaries, where a substring test would over-match. |
| `\|exists` | Tests presence only. `\|exists: true`. |
| `\|all` | Quantifier: all listed values must match. |

An absent, null, empty or `-` field never matches. Numeric-looking raw fields are
coerced to integers at load time so rules can be written as `LogonType: 3`.

Fields available are the normalized names plus the raw-source fields listed in
`docs/data_dictionary.md` under "Fields used by detection rules outside the
normalized schema". A field outside that list raises, which prevents a rule that
silently never matches.

## 4. Correlation rules

A correlation rule keeps an ordinary Sigma `condition` so the file remains valid
Sigma, and carries the real pairing in `x-correlation`:

```yaml
x-correlation:
  parent: parent
  child: child
  join_field: process_guid -> parent_process_guid
  scope: same dataset, exact host string, both event times resolved
  window_seconds: 5
  window_tests:
    - window_seconds: 0.606
      expect: no match
    - window_seconds: 0.607
      expect: match
```

`correlate()` in `scripts/test_all.py` is the only implementation. It enforces:

- **ProcessGuid join only.** DS002 has no ordinary Sysmon `ProcessId`, and
  hexadecimal and decimal process identifiers cannot be joined.
- **Exact host string match.** Host aliases are never merged.
- **Same dataset.**
- **Resolved event times only.** Non-Sysmon records have no trustworthy event time
  and cannot be ordered, so they are excluded from correlation entirely.
- **Forward-only**, `0 <= delay <= window_seconds`.

### The window matrix is mandatory

`window_tests` must contain the exact observed delay and the value immediately
below it. The three shipped rules assert:

| Rule | Observed delay | Asserted boundary |
| --- | --- | --- |
| CT-C01 | 0.607 s | 0.606 no match, 0.607 match |
| CT-C02 | 0.023 s | 0.022 no match, 0.023 match |
| CT-C03 | 22.175 s | 22.174 no match, 22.175 match |

This is the test that proves the window is enforced rather than ignored. A harness
that always returned a match for any window would pass a rule with no window logic
at all.

**Ship the window well above the observed delay.** All three rules ship at 5 s or
30 s while the observed delays are 0.607 s, 0.023 s and 22.175 s. A rule pinned to
the observed value is a rule written for one sample.

## 5. How a status is earned

`scripts/build_coverage.py` scores mechanically from recorded results. It cannot be
influenced by prose.

| Score | Condition |
| --- | --- |
| 2 Covered | A rule matched its declared attack evidence **and** a tuning case shows the tuned rule with zero residual benign matches. |
| 1 Partially Covered | A rule matched its declared attack evidence, with no measured benign comparison. |
| 0 Not Covered | No rule matched declared attack evidence, or no rule exists. |

In this library exactly one technique reaches 2, because exactly one rule has both
a confirmed malicious match and a measured benign result. That is the intended
behaviour, not an oversight.

## 6. Adding a rule: checklist

1. Copy `rules/_template.yml`.
2. Confirm the technique exists in ATT&CK 19.2 and record its object version. In
   v19, Mshta T1218.005 is under **Stealth**, not Defense Evasion. Do not substitute
   an obsolete ID to satisfy a validator.
3. Find the evidence line. Use `docs/DSxxx-inventory.json` for the raw SHA-256 and
   the physical line number. Look the record up; do not guess.
4. Write the `detection` block. Prefer `|endswith` on paths, `|re` with `(?i)` for
   command content, and a product or service name rather than a broad cmdlet.
5. Fill `x-attack`, `x-severity`, `x-scope`, `x-evidence` and `x-benign-review`.
6. Run `scripts/test_all.py --rule <id>`. It must be `PASS`, and the declared
   evidence must show `n/n`.
7. Add at least one `negative_event_uids` entry. A rule with no negative has not
   been shown to discriminate.
8. If the behaviour is a sequence, add `x-correlation` with a boundary matrix.
9. Run the full `scripts/test_all.py`, then `scripts/tune.py` if a benign
   comparison exists, then `scripts/build_coverage.py`.
10. Commit. Record the result in `PROGRESS.md`.

## 7. Things that will fail, and why that is the point

| Situation | Outcome |
| --- | --- |
| Declared evidence does not match | FAIL |
| Declared negative matches | FAIL |
| Unsupported condition syntax | ERROR, rule rejected |
| Field not in the documented map | ERROR, rule rejected |
| `sigma check` reports an error or issue | FAIL for every rule in the run |
| Window matrix expectation wrong | FAIL, with the observed value in the notes |
| Processed telemetry SHA-256 differs from the normalization report | Harness stops before replaying anything |
| `x-benign-review.status` is `pending` | Technique capped at Partially Covered |

The last two are the important ones. A harness that replayed against unverified
data, or that let an untuned rule claim coverage, would produce confident and wrong
output, which is the specific failure this project exists to prevent.
