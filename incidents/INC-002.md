## 1. Summary

On the host recorded as `WORKSTATION5`, a user account `wardog` ran a command shell
that started `mshta.exe` with an inline VBScript URL. That script created a
`Wscript.Shell` object and used it to launch PowerShell with an interactive
`-noexit` switch. The PowerShell process immediately queried the Sysmon service by
name, which is security software discovery against a specific product. The session
was left open, so the operator had an interactive shell by the time the discovery
command ran.

The chain is short, contains no persistence and shows no privilege escalation, and
it is still a true positive: it is the delivery and discovery stage of an intrusion,
established by two independent logs and by a command line that is unambiguous.

## 3. Root cause analysis

### 3.1 What is established

The proximate cause is a document or script-driven execution path that used a signed
Microsoft binary as a loader. `mshta.exe` is on the Windows allow-list precisely
because so much legitimate software uses it, and it accepts a `vbscript:` URL that
is executed directly in memory. The inline script did nothing but create a
`Wscript.Shell` and run a command, which is a dispatch pattern rather than a
programme.

Two details in the command line carry the intent:

- The switch is `-noexit`. The session is deliberately kept open. An operator
  establishing interactive access does this; a scheduled task does not.
- The command is `Get-Service sysmon`. It names one specific endpoint sensor rather
  than enumerating services generally. Inventory scripts ask what is installed;
  this asks whether one particular control is present.

The process chain is confirmed twice, and the parent relationships agree across the
two sources, so the ordering of the chain is not an artefact of one log's field
semantics.

### 3.2 What is not established, and why

- **What delivered the `mshta` command line.** DS001 contains no document open, no
  browser or web request, and no file-creation record that leads to `cmd.exe`. The
  parent of `mshta.exe` is a command shell whose own parent is not captured. The
  delivery vector, which would be the Initial Access technique, is **not established**.
- **Whether the account was compromised.** The subject user is `wardog`. DS001
  contains no event 4624 and no event 4625, so there is no authentication record of
  any kind, let alone a failure series. The account question is unanswerable from
  this capture.
- **Whether this host is the same machine as DS002's `WORKSTATION5.theshire.local`.**
  The host strings differ. This project does not merge host aliases, so no
  relationship between INC-001 and INC-002 is claimed, and the two cases are
  **not** linked into one campaign on the available evidence.
- **What happened after the discovery command.** The capture ends. There is no
  subsequent process creation, no network activity from this host except Azure
  platform traffic, and no evidence of what the interactive session was used for.
  This is the most important limitation in the case: the intrusion is established
  at the discovery stage and nothing beyond it.

## 4. Recommended response, referencing the playbooks

1. **Containment.** Capture volatile memory before isolating, because the session
   was interactive and the operator may have typed further commands that never
   reached a process-creation log. Follow
   `playbooks/PB-01-compromised-service-execution.md` steps 1 to 4, which apply
   equally to an interactive session.
2. **Account response.** Reset `wardog` and review its sign-in history from
   authentication sources outside this capture. Follow
   `playbooks/PB-03-compromised-credential-use.md`.
3. **Eradication.** Search the estate for `mshta.exe` with a `vbscript:` argument
   using CT-001, and for `Get-Service` naming a security product using CT-010. Both
   rules replayed cleanly and are ready to deploy.
4. **Recovery.** Confirm the Sysmon service state on this host, which the operator
   was checking, and confirm that PowerShell script block logging is enabled: DS001
   has no PowerShell records at all, which is a collection gap this incident
   exposed.
5. **Detection feedback.** Deploy CT-001, CT-010 and CT-C01. Note that T1518.001 is
   Partially Covered only, because no clean-environment benign comparison exists for
   `Get-Service` naming a product.

## 5. Closure classification

**True positive.** Justification:

- Two independent log sources record the same chain with matching parent
  relationships: Sysmon event 1 at lines 275, 398 and 422, and Security 4688 at
  lines 4, 30 and 36.
- The command line is unambiguous. `mshta` with a `vbscript:` URL that constructs a
  `Wscript.Shell` to run PowerShell is not a pattern produced by ordinary software
  or by user error.
- The `-noexit` switch establishes deliberate interactive access rather than
  incidental execution.
- The discovery command names a specific security product, which is a stronger
  signal than generic enumeration and is the reason CT-010 keys on the product name
  as well as the cmdlet.
- No benign explanation is available for the combination, and the report does not
  rely on the absence of contrary evidence anywhere.

## 6. Detection gaps this incident revealed

1. **No script block logging on this host.** DS001 contains zero PowerShell
   Operational records, so CT-001's chain can be followed only through process
   creation. Had a rule needed the PowerShell command text rather than the command
   line, it could not have been written or tested against this host at all. This is
   a collection requirement, not a rule defect, and it is the single most valuable
   deployment recommendation from this case.
2. **No authentication telemetry.** Zero 4624 and zero 4625 records means the
   account question cannot be answered at all, and it is the same question that is
   unresolved in INC-001. Two independent hosts, two independent cases, the same
   collection gap.
3. **No delivery evidence.** The chain starts at `cmd.exe` with no recorded parent.
   Without browser, proxy or document telemetry the Initial Access technique cannot
   be assessed, which is why T1078 is the only Initial Access-related entry on the
   matrix and it is scored from a different rule entirely.
