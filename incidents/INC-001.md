## 1. Summary

A Windows service named `Updater` was registered on `WORKSTATION6.theshire.local`
to run as `LocalSystem` with a demand start type, and its binary path was a command
interpreter rather than a program. The Service Control Manager started the service,
the service started `cmd.exe`, `cmd.exe` handed off to PowerShell with a base64
encoded command, and the resulting PowerShell process disabled two of its own
logging and inspection controls, then retrieved and executed content from an
internal address on port 80. 22.2 seconds after the encoded PowerShell process was
created, it launched `whoami.exe`; the PowerShell module log records the command's
output as `nt authority\system`, which independently confirms the process was
running as the machine account.

Every step is recorded by at least one log source, and the process chain is
corroborated by two independent process-creation logs. The case is closed as a true
positive.

## 3. Root cause analysis

### 3.1 What is established

The proximate cause of execution on this host is the service installation recorded
at DS002:1213. A service whose binary path is `%COMSPEC% /C start /b ...` is not a
service in the ordinary sense: it is a scheduled command line that the Service
Control Manager will execute on demand as `LocalSystem`, without any user session.
Once it started, the Service Control Manager became the parent of the command
shell, which is why every subsequent process in the chain is outside any user
session.

The privileges of the chain are independently attested. DS002:2877 records the
`whoami` command's output as `nt authority\system`, so the account is confirmed
rather than inferred from the service registration.

The concealment is deliberate and is recorded in the script text itself. The same
script block disables ScriptBlock logging and forces the AMSI failure flag before
performing its download, so the intent is not in doubt: the operator was working to
remove the evidence trail that this very investigation depends on. The reason the
case can still be reconstructed is that the 4104 record was written before, or
despite, that action.

### 3.2 What is not established, and why

- **How the service was created.** The 4697 record's subject user is `pgustavo`
  and a type 3 network logon for the same account exists on this host
  (DS002:1209), but neither record has a resolved event time, and DS002 contains no
  event 4625, so it cannot be shown that the account was compromised rather than
  used by the operator. T1078 is scored Covered on the strength of a rule that
  matched this logon, but the **credential compromise question itself is unresolved**
  and is the most important open item in this case.
- **Whether the service was activated remotely.** See HUNT-001. The Service Control
  Manager's RPC traffic 0.578 seconds before the command shell has no identified
  remote source; the cross-host RPC that does have one occurred 2.2 seconds later.
  The case records this as unresolved rather than asserting lateral movement.
- **What the download returned.** No response content, packet capture or second
  stage script text exists in the capture. `T1105` is confirmed as an action, not as
  a payload.
- **Whether the command-and-control channel is established.** HUNT-002 concluded
  **inconclusive**: exactly one connection to 10.10.10.5 exists, and the resolved
  time base is 2 minutes 14 seconds.

## 4. Recommended response, referencing the playbooks

1. **Containment.** Isolate `WORKSTATION6.theshire.local` from the network while
   preserving volatile memory; the PowerShell process may still hold the retrieved
   second stage. Follow `playbooks/PB-01-compromised-service-execution.md`.
2. **Credential response.** Reset the `pgustavo` account and any account whose
   credentials could have been presented to the proxy. Follow
   `playbooks/PB-03-compromised-credential-use.md`. This is the highest-priority
   action because the credential question is the unresolved root cause.
3. **Eradication.** Remove the `Updater` service, then hunt the whole estate for
   services whose binary path references `powershell`, `cmd` or `wscript`. The
   detection is CT-011 and it is portable as written.
4. **Recovery.** Re-enable and verify ScriptBlock logging and confirm AMSI is
   functioning, since the operator disabled both on this host. Restore from a known
   good state rather than cleaning in place.
5. **Detection feedback.** Deploy CT-002, CT-003, CT-005, CT-006, CT-007, CT-011,
   CT-C02 and CT-C03. Note the standing limitation: these are Partially Covered,
   not Covered, because no clean-environment benign comparison exists.

## 5. Closure classification

**True positive.** Justification, in the terms of the project's own contract:

- The behaviour is confirmed by at least two independent log sources. The process
  chain `services.exe` to `cmd.exe` to `powershell.exe` to `whoami.exe` appears in
  both Sysmon event 1 and Security 4688, and the parent relationships match in both.
- The privileged context is confirmed by recorded command output at DS002:2877,
  not inferred from a configuration field.
- The concealment actions are present verbatim in recorded script text.
- No benign explanation is available for a service whose image path is a command
  interpreter, running as `LocalSystem`, whose payload disables the two controls
  that would have recorded it.
- Every claim above cites a source line. Where a claim could not be supported, it
  appears in section 3.2 as unresolved rather than in the findings.

## 6. Detection gaps this incident revealed

1. **Service installation is not correlated to service execution.** The most
   important record, DS002:1213, has no resolved event time, so the persistence
   mechanism cannot be placed in the timeline by clock. A correlation rule joining
   4697 to the Sysmon execution within one host would close this, but it cannot be
   written or tested here because the timestamps are unresolved. Recorded as the
   top telemetry request in `coverage/matrix-v2.md`.
2. **LSASS access alerting is unusable in this environment.** CT-013 was authored
   and tuned; all seven LSASS access records in DS002 are attributable Windows
   activity through `lsm.dll` and `sysmain.dll`, and the tuned rule correctly
   matches none of them. T1003.001 stays Not Covered. This incident did not
   involve credential dumping, and the report records that the absence of such
   access in this capture is not evidence that it never happened.
3. **Coverage is asymmetric across hosts.** The same technique set is covered by
   rules on DS002's host and by a completely different rule set on DS001's host,
   because each host has only a handful of process-creation records. A client
   estate would not have this problem; a two-minute capture does.
